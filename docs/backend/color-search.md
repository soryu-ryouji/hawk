# 颜色提炼与颜色检索

复刻 Eagle 的功能：为每张图片提炼出一组代表颜色（调色板），展示在详情面板中；点击色块后按颜色检索全库中含有相近颜色的图片。

## 功能分析（Eagle 的行为）

从截图观察到的行为：

1. 详情面板在预览图下方展示一排圆形色块（约 10 个），为该图片提炼出的代表颜色
2. 选中色块显示其十六进制值与覆盖占比，如 `#344441 (3.1%)`——占比 = 该颜色在图中的像素覆盖比例
3. 点击色块触发检索：列出全库中调色板含有相近颜色的图片

## 实现原理

### 颜色提炼

「代表颜色」不是平均色，而是对像素做**聚类/量化**：把成千上万种像素颜色归并到 K 个簇，每个簇取一个代表色，簇的像素数即占比。步骤：

1. 解码图像，降采样到小尺寸（64×64）——提速并抹掉噪点，对结果无可见影响
2. 量化聚类到 K=10 个颜色。实现为手写 **median-cut**
3. 统计每个量化色的像素数，得出占比；按占比降序取前 10

纯色图会得到 1 个颜色，渐变图得到一组渐变色——均属正常输出。

### 颜色检索

检索不是精确匹配 hex（提炼出的颜色几乎不会恰好相等），而是**感知相似度**匹配：

- 色彩空间用 **CIELAB**（感知均匀：数值距离与人眼感受的差异成正比）。RGB 欧氏距离感知不均匀；HSV 的色相在低饱和度（灰、黑、白）时不稳定，都不合适
- 距离用 CIE76 ΔE（Lab 空间欧氏距离）。查询色与图片调色板中**任一**颜色的 ΔE ≤ 阈值（25，经验值，可调）即命中
- ΔE 参考尺度：< 2 人眼难辨；10 左右明显不同但同色系；25 大约覆盖「同一颜色家族」。Eagle 的检索手感大致是这个宽松度

## 方案设计

### 数据流

调色板是内容派生数据（同内容必同结果），与缩略图同属「可重建的本地缓存」，完全复用缩略图的生命周期模型：

```text
入库/扫描 → IndexPipeline（单写者）
  → 派发后台 worker（与缩略图同一队列）
      解码图像 → 提炼调色板（缩略图生成时顺带，零额外解码成本）
      → 提交 PaletteJob 回流水线 → 写入元数据 TOML → item.Palette 更新 → 发 item.updated
启动复用路径（哈希复用、不读文件内容）
  → 调色板随元数据 TOML/SQLite 镜像直接注水索引
  → palette 缺失 → 派发 palette-only 任务到 worker 补齐
```

要点：

- **计算时机挂在缩略图 worker 上**：生成缩略图时图像已解码，顺带提炼，零额外解码成本。仅调色板缺失而缩略图齐全时，解码最小的已有缩略图（256px WebP）而非原图，避免为补缓存全库解码原图
- **单写者规则不破**：worker 不直接改索引，计算结果经 `PaletteJob` 回到流水线消费循环应用；job 携带 hash，若期间内容已漂移（item 不存在或 hash 变化）直接丢弃——幂等
- **写元数据（2026-02 设计修订）**：调色板是内容的纯函数，同 hash 各平台/各设备计算结果必然一致，直接入 `.hawk/metadata/<hash>.toml`（`[[palette]]` 表）——一台计算全平台复用，无派生缓存与双写

### 缓存镜像

SQLite 派生缓存 `index.db` 的 `items.palette` 列镜像 TOML 中的调色板（本地专用、可重建，见 storage.md），存储格式为纯 JSON 数组：

```json
[
  { "color": "#344441", "percentage": 3.1 },
  { "color": "#6b7f7a", "percentage": 12.4 }
]
```

- 按占比降序，最多 10 个；percentage 为 0–100、保留 1 位小数，与 Eagle 展示口径一致
- 镜像随 schema 版本整库重建，与 TOML 始终同源

### 索引与查询

- `Item` 增加 `Palette` 字段：内存中每项同时保存 RGB（展示/缓存用）与预算好的 Lab（查询用，避免每次查询全库做色彩空间转换）
- `ItemQuery` 增加可选 `Color`；`ItemIndex.Query` 在现有线性过滤中增加一段：查询色转 Lab（一次），逐 item 检查调色板任一项 ΔE ≤ 25
- 性能：10 万 item × 10 色，纯浮点比较，毫秒级；与现有过滤同为锁内线性扫描，无需倒排索引（符合 storage.md 对磁盘索引的既定立场）
- 与其他过滤条件组合逻辑为 AND；回收站视图同样适用

### API 变更（server-rest-api-v1.md）

**Item 对象增加字段**：

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| palette | object[] | 调色板，按占比降序，最多 10 项；尚未提炼或不支持解码时为空数组 |

palette 项：`{ "color": "#344441", "percentage": 3.1 }`。color 为小写 `#` 前缀 hex。

**item/list 请求增加参数**：

| 参数 | 类型 | 说明 |
| ---- | ---- | ---- |
| color | string | 按颜色检索（如 `#344441`，`#` 可省略，大小写不敏感）；命中条件为调色板任一颜色 ΔE ≤ 25。格式非法返回 `INVALID_PARAM` |

无新端点、无新事件类型（调色板异步就绪后复用 `item.updated` 推送，与缩略图补齐的模式一致）。

### 前端变更

- **Inspector.vue**：预览图下方增加调色板色块行（圆形色块，最多 10 个）。hover 提示 `#344441 (3.1%)`；palette 为空（未就绪/非图像）时整行隐藏
- **点击色块 = 在当前范围内检索**：不切换视图，直接在当前查询上叠加 `query.color`——在「全部素材」下即全库检索；在某个文件夹/分类/标签下则只在该范围内过滤（AND 语义），与 Eagle 一致。当前检索色对应的色块显示选中圈
- **TitleBar.vue**：颜色检索激活时显示一个 chip（色点 + hex + ×），× 清除条件；点击其他色块替换条件。颜色条件属于 query 状态（与关键词、评分同级），清除前切换文件夹/分类/标签时继续生效
- **store**：`QueryState` 增加 `color?: string`，`buildListParams` 透传
- `schema.d.ts` 由 gen-types.mjs 重新生成

本期不做 Eagle 的全局彩虹色条选色器（在筛选面板上直接选任意颜色）。底层检索能力（`color` 参数）已具备，色条只是另一个入口，需要时后续再加。

### 常量

| 常量 | 值 | 说明 |
| ---- | ---- | ---- |
| 调色板大小 | 10 | 量化器 MaxColors |
| 分析尺寸 | 64×64 | 提炼前降采样 |
| 匹配阈值 | ΔE 25 | CIE76，调色板任一色命中即中 |
| 缓存版本 | 2 | 算法变更时 bump（当前为 median-cut） |

### 边界情况

- 非图像文件 / 解码失败：palette 为空，永不命中颜色检索（与缩略图「尽力而为」一致）
- 动图（GIF/APNG）：取首帧
- 透明像素：alpha < 128 的像素不参与统计；全透明图 palette 为空
- id 漂移：内容变化 → 新 hash → 重新提炼，旧缓存在内容无引用时清理
- 灰度/CMYK：解码统一转 RGB，无特殊处理

## 备选方案与取舍

| 方案 | 为何不采用 |
| ---- | ---- |
| 纯内存、不缓存调色板 | 每次启动需全库解码（或用缩略图解码 1 万张约数十秒），启动后检索长时间不完整。缓存文件只有几十字节/张，成本极低 |
| 调色板写入 metadata TOML | 违反「派生信息不入元数据」原则；参与同步会因算法版本差异制造冲突 |
| RGB/HSV 距离 | RGB 感知不均匀；HSV 色相在低饱和度下不稳定（灰色会匹配到任意色相） |
| 固定色相分桶 + 倒排索引 | 内存线性扫描已是毫秒级，无需索引结构；分桶还会把桶边界上的相近色错配 |
| 手写 k-means/中位切分 | Rust 生态无成熟 Wu 量化器实现，手写 median-cut（v2），质量与 Wu 相当 |

## 实施状态

已实现（2026-08）。审批确认的结论：

1. 调色板落库外缓存目录的 `colors/` 缓存文件（与缩略图同模型）
2. 调色板 10 色、ΔE 阈值 25（可按真实图库调参）
3. v1 只做单色检索（点击色块，在当前视图范围内过滤）；多色组合与全局色条选色器留待后续

实现与本文档的一处偏差：PaletteJob 写队列失败时不置溢出标记，直接丢弃——缓存文件已落盘，周期对账扫描会由 ApplyUpsert 载入，代价相同且逻辑更简单。
